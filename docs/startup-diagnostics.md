# Startup timings

Development pages send a startup timing report automatically, one second after notes reach the second animation frame. Built production pages require `?startup-profile=1`. The second frame is a presentation approximation, not a browser paint measurement. A 12-second waiting checkpoint also reports progress if the account has already been verified. Reports use monotonic times relative to navigation, so stages can be compared without synchronized client/server clocks.

If cooperative indexing is still running when the first ready report is sent, collection continues until it finishes or for at most 12 more seconds. A follow-up replaces the same navigation's report, adding search completion and work counters without changing the original notes-frame time.

Reports include navigation and script request timings, the session request and server authentication duration, IndexedDB open/read/apply/write/compaction checkpoints, tab state-vector encoding, note projection, DOM/frame presentation, cooperative search preparation, and initial synchronization. Counts describe update records and bytes, notes, checklist records, and history records. Animation-frame gaps work in Firefox as well as Chromium; they include scheduling delays and are not direct CPU measurements.

The browser posts to `/api/diagnostics/startup` with its verified `X-Stow-Vault`. An authenticated GET to the same endpoint, with the same expected-vault header, returns the latest 20 reports for that account. The server keeps at most 100 reports total in memory; a restart clears them. Repeated checkpoints for a navigation replace the earlier report. Data contains numeric timings and counts, script paths without query strings, and the browser user agent. Note contents, labels, cookies, and authentication headers are excluded.

Use `marks` to subtract consecutive checkpoints. Resource timing for `/api/session` separates the network request from later JavaScript scheduling and body parsing; `serverMs` records just the Stow authentication handler, excluding nginx and its authentication integration. `updateCount` and `updateBytes` describe the local update log. Loading applies those records in one Yjs transaction, without merging them into another byte buffer first. The interval between `account-opened` and `notes-frame` covers rendering and any intervening main-thread work; synchronization marks reveal overlap.

Diagnostic uploads never block opening or syncing notes. An unavailable endpoint only produces a console warning. Offline startup does not authorize uploads from a cached identity; the server must verify the account first.

`broadcastBytes` counts the initial state vector, excluding its small message envelope. It does not include later peer replies. `search-build-start` and `search-build-end` delimit the first cooperative build, including time yielded to other tasks. `searchActiveMs`, `searchSlices`, `searchMaxSliceMs`, and `searchIndexedNotes` count preparation work completed before the report, including incremental builds. Tasks aim for 4 ms and yield between note fields/checklist items; an individual Markdown parse or garbage collection may exceed that budget. These timings describe elapsed execution, not CPU profiling samples.

The Vite development server also records the last 200 requests for the main module, React DOM dependency, and icon dependency in `../build/startup-http.json`. This disposable file is denied by Vite's file server. It records actual response status, content length, cache directives, ETags, and the browser version to distinguish cache revalidation from full responses. It excludes cookies, proxy identity/proof, account data, and unrelated URLs. No response or request headers are changed by this observer.
